# Changelog

## [Unreleased]

- Studio accepts the provider connection test's `not_testable` status and `dataset`, and `GET /providers`' `last_test` (kpubdata-builder#842). `not_testable` — Builder found no Source Dataset it could call without guessing a parameter — is shown as neutral "Not testable", never as a key failure. Without this, the contract-drift check failed against Builder main and a `not_testable` response would not parse.

### Added

- **Users and sign-up approval on the Administration page** (#409). Over KPubData Builder's sign-up ledger (kpubdata-builder#785, contract 1.54+), `/admin` lists everyone who has signed in through OIDC — display name, the irreversible user id as a short hash, the sign-up status, first and last sign-in, and who decided (the allowlist or an administrator's hash) — with how many are awaiting approval. **Approve** and **Reject** ask for confirmation, then show the entry Builder returns; a 403 or 404 on a decision is shown as a refusal and the row keeps its status. A non-administrator reaching the page by URL sees Builder's 403, an empty ledger (a deployment without OIDC) says so, and a Builder older than the ledger says it has none. The ledger schemas strip unknown fields, so a token a Builder might add never reaches the screen. `builderApi` gains `adminUsers`, `adminApproveUser` and `adminRejectUser`.
- **Connections shows each provider's last test and a Test action** (#566, kpubdata-builder#842). The Last test column reads `last_test` from `GET /providers` — the result KPubData Builder recorded for this account, with its time and the dataset it called — instead of `—`; never tested reads "Never tested", and a Builder that does not send `last_test` still shows `—`. `not_testable` and `not_configured` are quiet text, never a key failure; only `failed` is a badge. Each row's **Test** calls `POST /providers/{provider}/test`, which since kpubdata-builder#842 calls a dataset that needs no guessed parameter and no application, and shows the result in that row. A test request that fails is a page error, not a key failure. Preview still decides whether a chosen source dataset works.

- **Refresh History names each run's table and snapshot** (#567, kpubdata-builder#844). The Table column shows `dataset_title` with its `dataset_id`, linked to Table Detail, and the Snapshot column the `snapshot_id` the run committed — or each of `snapshots` when it committed several — instead of `—`. A run that committed nothing reads "None"; a Builder that does not send the fields still shows `—` with the reason. A **Table** filter (`?table=`) lists the tables the loaded runs name and is left out when there are none. `GET /builds` is now parsed with a zod schema (`buildSummarySchema`), with the new fields optional so an older Builder still parses; run titles also reach Home's recent runs and the run detail.
- **⌘K / Ctrl+K finds tables and sources, not only pages** (#533). The search dialog is 560px wide and matches the caller's tables (`GET /datasets`, by name, id or source) and the catalog's sources (`GET /catalog`, by title, provider or name) as the user types, grouped as Tables · Sources · Pages, with identifiers in monospace; a table opens Table Detail and a source opens the Catalog filtered to it. The Tables and Catalog list filters follow, and **Ask KPubData: "…"** is offered only as the last option — never the one Enter picks by default. Arrow keys and Enter are enough, and the dialog fits a 390px screen. The lists load the first time the dialog opens; one failing leaves the other searchable and says so in one line. Searching columns across tables waits for Builder support.
- **A table explorer and a visible `FROM dataset` binding in the SQL Workspace** (#528). On a KPubData Builder with a warehouse, a 256px explorer lists committed warehouse tables as Table → Source → Column — split from `logical_name` (`<dataset_id>.<source_key>`), because `WarehouseTable` carries no provider — and loads a table's columns only when it is expanded, from one `POST /warehouse/rows` page (`page_size: 1`, no count). It is a keyboard tree (↑/↓, →/←, Home/End, Enter/Space). Picking a source binds `dataset` to it, so picking → Run is two clicks; picking a column inserts its identifier at the editor's cursor and runs nothing. A binding bar reads `dataset → <table> @ <snapshot>`, a table's own name in `FROM`/`JOIN` gets a note before running, and the result footer says rows · time · snapshot · rev · LIMIT — the row cap Studio now sends explicitly (100, the contract default), with no total the Builder did not give. The table select is replaced by the explorer. A deployment without a warehouse says in one line that the explorer needs one.
- The SQL Workspace shows each warehouse snapshot's fetch coverage from Builder (builder#816): every snapshot option says complete, partial or unknown, and a note under the picker gives the selected (or current) snapshot's word with fetched/reported row counts and reasons. A snapshot without a coverage record, or with a status this Studio does not know, reads as unknown — never complete (#417).
- **Export a query result through Builder only** (#501). The SQL Workspace's **Export** sends the table, the pinned snapshot and the SQL to Builder's `POST /warehouse/exports` (builder#819), which checks the source's licence and PII policy and refuses a result over the row or size limit instead of cutting it. Studio shows the manifest — the concrete snapshot and revision read, the terms verbatim, that the result is user-derived, fetch coverage (unknown when not recorded), cells the spreadsheet profile changed, expiry — and downloads Builder's zip with the person's own credentials. A refusal is shown as a refusal with nothing kept. The spreadsheet profile's note says a BOM only helps Excel read UTF-8 and does not stop leading zeros, large integers or dates from being converted. A test fails if any screen builds a CSV or a result `Blob` in the browser.
- **Charts that say what they cover** (#500). The SQL Workspace draws bar and line charts — from a warehouse table through Builder's `POST /warehouse/aggregate` (builder#818), which aggregates every filtered row before sorting and cutting to the group limit, and from any SQL result with **Show as chart**. Every chart states its scope: all groups, the top N by a stated order of how many groups, based on the N rows a cut result returned (never called the top N, the whole or a sample), or a named sample. A missing value is drawn as a gap, not 0; a time axis is sorted by time; a Decimal is plotted approximately but its tooltip shows the exact text. A `sum` needs the person to state the column is additive. A stored `ChartSpec` is checked for version, size, depth and a readable table before use. No chart library is added — the charts are SVG.
- **One data table for Builder values** (#499). SQL results, stage samples and table pages are drawn by `DataTable`: every cell goes through `cellValue` (a zero-led code, a 19-digit code, an unsafe integer, a Decimal, null and a date show as sent), headers show the display label, logical type and unit from Builder's column hints (builder#813) and mark an inferred one, and the footer says how the total is known — exact, estimated, not computed or unknown — never writing a missing total as 0; a cut SQL result no longer implies one. The SQL Workspace can **Browse rows** of a warehouse table through `POST /warehouse/rows` (builder#815): the first page asks for `current`, and every later page asks for the snapshot the first one named, so a refresh committed in between does not splice two snapshots.
- **Saved Analyses** (`/analyses`, #417): on a KPubData Engine with a warehouse, SQL Workspace queries committed tables — pick a table and a snapshot, `current` being pinned when the query starts — and **Run and save** keeps the SQL with the concrete snapshot it read (kpubdata-builder#783). Saved Analyses lists them; **Run again** reads that same snapshot after the table has been refreshed, **Open in SQL Workspace** loads it, and **Delete** releases its hold. Every result names what it read (`table@snapshot · rev N`). A deployment without a warehouse keeps the run-based SQL Workspace and says analyses cannot be saved there. The ANALYZE menu gains Saved Analyses.
- Tables and Table Detail show a table's five status axes — Health, Completeness, Refresh, Access, Maturity — as separate badges, each naming its axis and its word (#422), from KPubData Engine's `status_axes` (kpubdata-builder#781). `unknown` is shown, not hidden, and Maturity is always neutral because it is a grade, not a condition. An Engine that does not send the axes shows `—` (#524).
- Studio builds into a container image (#411): `Dockerfile` puts the static build behind unprivileged nginx, and the Builder URL and OIDC settings are read from the container's environment at start (`BUILDER_API_URL`, `USE_REAL_BUILDER`, `OIDC_ISSUER`, `OIDC_CLIENT_ID`) into `/config.js`, so one image serves every deployment; unset values fall back to the build-time `VITE_*` ones. A value that could break out of `config.js` stops the container instead. Publishing the image from the release workflow, with a smoke test of two deployments, follows separately.
- CI compares Studio's response schemas with Builder's contract (kpubdata-builder#693). For every contract schema Studio mirrors by name, a contract enum value Studio does not accept, or a key Studio requires that the contract does not define, fails the `Builder contract drift` job, which the CI gate requires. It reads the contract from Builder's main; locally, set `BUILDER_CONTRACT` to run it.
- **Administration** (`/admin`, #409): the policy in force (`ENFORCE_OWNERSHIP`, the server publish-credential fallback) and every owner's runs, metadata only, owners as short irreversible hashes. The menu entry appears only when KPubData Engine answers `GET /admin/config` with 200; a 403, an Engine without the admin role or any other failure hides it. Hiding is a convenience — reached by URL, the page shows the Engine's 403 as "not an administrator". The admin responses are parsed strictly, so a credential an Engine might add never reaches the screen. Listing users and approving sign-ups waits for an Engine API (kpubdata-builder#785).
- **SQL Workspace** (`/sql`, #417): query one table snapshot — pick the table, the run (snapshot), the stage and, for a multi-source run, the source, then run the SQL yourself; `FROM dataset` reads that snapshot, and the result names it (`table@run · stage · source`). It sits first under ANALYZE, and Table Detail's **Query** opens it pinned to the run you are looking at. The target lives in the URL, so a link reproduces it. Joining tables waits for KPubData Engine multi-table SQL (kpubdata-builder#704) and saving an analysis for server storage (kpubdata-builder#783). Mock mode answers with demo rows, labelled demo.
- Connections shows **where to apply** (#412): every source dataset the catalog marks as needing an application, grouped by the page where the application is made — one application can unlock several — with a direct link, the provider's daily cap and a guide to moving to an operational account on data.go.kr. A cap the spec does not state, and today's usage (KPubData Engine does not count calls per key), read as unknown, never zero; datasets whose catalog entry says nothing about an application are counted as unknown, not "not needed". The catalog's `quota` is optional until KPubData Engine sends it (kpubdata-builder#778).
- The visual identity is written down in `docs/brand/VISUAL_IDENTITY.md` (#425): the `KPubData` wordmark leads and `Studio` is a weaker suffix, brand and status colours are separate tokens (warning, stale and partial share amber and differ by label), SQL and identifiers are always monospace, and density comes before marketing type. Five static warehouse prototypes — Home, Catalog, Tables, Table Detail, SQL Workspace — live in `docs/prototype/warehouse/` with desktop and 390px screenshots, awaiting prototype review before the app adopts them. A test fails if a status token takes a brand colour or a prototype badge carries no word.
- Studio says when it is talking to a Builder from another release (#430). It compares its own build version with the `version` that `GET /version` reports: a minor or major difference shows one dismissible banner line and blocks nothing, a patch difference passes with a console note, and a Builder that does not report `version` gets no warning. The `api_version` contract check is unchanged and separate.
- A real-Builder E2E for the warehouse path (#417): `e2e/real-saved-analysis.spec.ts` builds the replayed public-API table through KPubData Builder (`serve --replay`, kpubdata-builder#837), opens it from Tables, queries it in the SQL Workspace, saves the analysis, builds the table again so its current snapshot moves on, and re-runs the analysis from Saved Analyses — which must read the snapshot it was saved with, not the new one. It runs with `npm run test:e2e:real`.

### Changed

- **CI's E2E job runs in the Playwright image** (#585). The job now runs in `mcr.microsoft.com/playwright:v1.63.0-noble` on `ubuntu-24.04` instead of downloading Chromium with `playwright install --with-deps` onto `ubuntu-latest`, so browsers, system libraries and fonts come from the image for the installed `@playwright/test` — the same image the screenshot baselines (#532) are rendered in — and do not change when the runner image does. `__tests__/e2eContainerImage.test.ts` fails when the image tag and the installed `@playwright/test`, `playwright` and `playwright-core` versions differ, so a Playwright bump has to move the tag with it.

- **One table creation flow in three steps** (#534). Creating a table is `/add` alone: **Configure** (the source choice with its settings, credentials, request parameters and data.go.kr application in one step) → **Preview & Validate** → **Create**, which now shows the logical name each source's table will get — the table ID and the `source_key` from KPubData Builder's preview, never derived in Studio, and nothing before a fresh preview. `/refresh-jobs/new`, the second seven-step wizard, redirects to `/add` with its query, so Workspace's **Open saved spec** (`?savedSpecId=`, now also for file and URL sources) and Ask KPubData's table draft land in this flow. An Ask KPubData draft that cannot become a spec — a credential redacted in storage, a partial draft, parameters that are not JSON — is no longer dropped: it stays saved, the error is shown, and its provider, source dataset, table ID and title are filled in so only the request parameters are typed again. When both a draft saved in `/add` and an Ask KPubData draft are waiting, the banner asks which to open and deletes the other. Its template step is gone. Editing an existing table's spec stays at `/refresh-jobs/:id/edit`, keeps what the form cannot express (#496), no longer shows the template step, and opens only once the spec is in the form. **The edit page no longer has Save draft**: its draft slot was the one the creation flow reads, so a half-edited spec leaked into the next new table; an edit is saved by running it, or kept in Workspace with Save this spec.

- **Studio releases only in the monthly window** (kpubdata#685): `release.yml` runs kpubdata's `release-window` gate first on both the prepare and the release path, and refuses a release outside the week holding the month's last Thursday (KST). A critical patch — a security fix or a release-blocking defect — passes only when it names its issue: `critical_patch` and `critical_issue` on a dispatch, or a `Critical-Patch: #N` line in the release pull request, which the prepare job writes. AGENTS.md says kpubdata is no longer on this train: it releases on demand, at most once every seven days.
- **Tables and Home read each table's current snapshot from the warehouse table list** (#569, kpubdata-builder#841). `GET /warehouse/tables` now summarises each table's current snapshot (`current_snapshot`: id, row count, commit time, coverage) and names its dataset (`dataset_id`), so the Tables list and Home's recent snapshots no longer ask `GET /warehouse/tables/{name}` once per table. A table is matched to its dataset by Builder's `dataset_id` — a dataset id may contain a dot — and one Builder cannot attribute is left out rather than guessed from its name. Home's run column reads `—` for a snapshot from the summary, which does not name the run (Table Detail does). An older Builder that omits the fields keeps working: its tables are joined by name and read one detail each, four at a time, as before. The demo warehouse lists its tables with the summary.

- **Quality Center reads every table's issues in one call** (#568, kpubdata-builder#843). The page asks `GET /quality/issues` once — following its cursor, 500 rows a page — instead of listing the first 100 tables and asking `GET /builds/{run_id}/quality` for each, four at a time; a workspace with more than 100 tables is no longer cut. The coverage line now shows Builder's own counts — tables evaluated, partially evaluated, not evaluated (N/A) and unreadable, none counted as passed — and the number of issues. The Table filter lists the tables that have issues; a table in the URL that has none is checked with one filtered call so "no issues" and "no such table" stay apart. A Builder without the endpoint (before contract 1.49.0) answers 404, and the page falls back to the per-table reads, saying when it read only the first 100 tables.

- **The demo shows tables and snapshots, and only what Builder sends** (#530). Without a Builder (GitHub Pages, `npm run dev`), Studio now has a demo warehouse: four tables named `<dataset_id>.<source_key>` after the demo datasets, each with snapshots produced by the demo runs — ids, row counts, commit times, one quarantined snapshot, coverage `null` (unknown) — so Home's recent snapshots, the Tables snapshot and row columns, Table Detail's snapshot view with Schema and Preview, and the SQL Workspace's table explorer all show the warehouse path. Row pages are generated from the row index so paging holds together; a query, aggregate, export or saved analysis says the demo needs a Builder instead of inventing a result. The warehouse screens choose Builder or demo in one place (`features/sql/warehouseApi.ts`); `builderApi` keeps no mock branch. Demo fixtures no longer make up institution names or catalog descriptions, and their sources use the provider named in the source key. `__tests__/demoFixturesContract.test.ts` parses every demo fixture (datasets, runs, stages, quality, warehouse, catalog, the MSW catalog) with the contract's zod schemas and fails when a fixture carries a field the schema would strip or names an institution or licence.
- **Table Detail Preview says what it is paging** (#537). On a KPubData Builder with a warehouse, Preview pages the snapshot on screen through `POST /warehouse/rows` with the shared `DataTable`: every page names that snapshot id, so a refresh committed while paging does not change what is read, and the footer says how the total is known (exact, estimated, or not computed — never 0). Without a warehouse, Preview is the run's stored stage sample: its footer now says **N rows · sample** instead of pairing it with the stage's run row count, and it has no paging.

- **No English UI text is typed straight into a screen any more** (#531). About 120 labels written directly in TSX — Table Detail's tabs, `Data Passport`, the run view's headings and table headers, the Provider filters, the publish, run-detail, report, SQL and Add data labels — now come from the locale files with the text they showed, so the product does not change; where the old text broke a naming rule it follows the rule instead: the Ask KPubData context bar and the report form say Table, not Dataset; publish readiness, the Settings base URL and a run's error say KPubData Builder; the Ask KPubData page eyebrow and the Settings privacy note no longer say "assistant". The run-based Table Detail view reuses the translated keys the warehouse view already has, so its tabs, tab list label and sample heading read 개요 · 스키마 · 미리보기 · 품질 and 샘플 데이터 in Korean as the snapshot view does. `npm run i18n:check` now also fails on English UI text in TSX — JSX text, a string rendered as a child or from a conditional, a prop a person reads (`label`, `title`, `placeholder`, `aria-label`, `alt` …) and a `label`/`title` kept in a constant — each also as a template literal, whose fixed parts are read with every `${…}` as a space (`` `Run ${id}` ``, `` `${n} columns` ``) — while brand names, formats, Builder's status codes and stage names, identifiers, URLs and `<code>` stay allowed (`scripts/hardcoded-ui-text.mjs`); an `i18n-ignore` marker exempts the line after it only when it sits on a comment line, so a marker at the end of a code line exempts that line alone. The terminology gate reads the same TSX text with no exemption and fails on Assistant, Kubi, Refresh Jobs or a bare Builder, and on Assistant, Kubi or Refresh Jobs in a locale value. The command palette's Ask row hint says AI instead of Assistant. The stale-UI-literal gate no longer matches a removed word inside an identifier that a current value follows (`isAssistantDemoAvailable`), and a test line that asserts a retired word is gone can say so with `stale-ui-ignore: <reason>`.

- **Home leads with tables that need attention and recent snapshots instead of run KPIs** (#527). The four KPI cards (TABLES, RUNS SUCCEEDED 24H, QUALITY WARN 24H, RUNNING), the recent quality list, the workflow strip and the first-run tour over the screen are gone, and Home no longer asks for `/monitoring/*` or `/quality/summary`. On the left: **Tables that need attention** — only Stale, Degraded, Partial, Failed or an Access problem from `status_axes`, each an axis-and-word badge, the section left out when there are none — and **Recent snapshots**, each warehouse table's current snapshot newest first (table · snapshot · rows · committed, with the run only as the last column). On the right: **Recent analyses** (opens in the SQL Workspace) and **Connections that need attention** (Access problems grouped by provider, to Connections). Every item is one click from its table or analysis; the header action is **New SQL query**. A deployment without a warehouse keeps the recent runs list and says why in one line; someone with no tables and no runs gets the two ways to start — find a source in the Catalog, or add data from a file.

- **Table Detail opens on the current snapshot, with no run, source or stage to pick** (#526). On a KPubData Builder with a warehouse, the header is the table's title, its identifier in monospace and provider, the status axes that need action, and **Ask about this table** · **Refresh** · **Query**; the tabs are Overview · Schema · Preview · Quality · Snapshots. Overview shows the snapshot id, commit time, rows, revision and fetch coverage from `WarehouseSnapshot.coverage` (partial is a badge, a missing record is Unknown), and the run that produced it, in monospace, as provenance. Schema lists the snapshot's columns with Builder's type, display name and unit (`POST /warehouse/rows`, one row); Preview pages the snapshot's rows; Quality reads the producing run's results for that source. A past snapshot is chosen only in the Snapshots tab (`?snapshot=`), whose rows carry run detail, edit spec and publish in an overflow, with the dataset's runs below. A dataset with several sources switches between its source tables. Ask KPubData gets the snapshot's run and source, never a guessed stage. A deployment without a warehouse, or a table with nothing committed yet, keeps the run-based view with its pickers and says why in one line.

- **Tables lists each table by its current snapshot, rows and the status axes that need action** (#525). The columns are Table (identifier in monospace, title and provider under it) · Current snapshot · Rows · Health · Completeness · Refresh · Last refreshed; the stage summary, the Validation column and the Stage and Validation filters are gone, and a **Needs attention only** filter (`?attention=1`) keeps tables with an actionable axis. Snapshot, rows and commit time come from the current snapshot in `GET /warehouse/tables/{name}` (one request per committed table, four at a time; builder#841 asks for them in the list), joined to `GET /datasets` by the `<dataset_id>.<source_key>` name; a table with several sources shows one line per source, never a sum. Statuses follow the #524 state model — plain text when fine, an axis-and-word badge when actionable, an Access problem under the table name — and anything Builder did not send is `—`. A deployment without a warehouse hides the snapshot and row columns and says so in one line. Rows open Table Detail by click or Enter/Space.

- **Monitoring reads as key-value panels instead of tabs of cards** (#539). One page, top to bottom: KPubData Builder health — Builder API (status, P95 latency, samples), Queue (waiting, running, total), Workers (active / capacity, utilization) and the Snapshot store (last write) as key-value rows — then refresh outcomes for the last 24 hours, then recent refreshes as a table whose run ids link to their detail. A healthy value is plain text; partial, not measured and degraded are badges. A measurement Builder sent as null, and every count of an aggregate Builder could not measure, is `—`, never 0. Auto refresh is a "Refresh every 30 seconds" checkbox. A 401/403 is one line saying the page needs an operator account, not an empty screen; the hourly bar chart is gone.
- **A narrower sidebar and a quieter topbar** (#523). The sidebar is 232px (the `w-sidebar` theme token, down from 288px) so result tables get the width; collapsing it and the mobile overlay work as before. The topbar is the breadcrumb on the left and three things on the right: **Search** (⌘K / Ctrl+K) jumps to a page or searches Tables and the Catalog by name and never starts an AI conversation, **Ask KPubData** is the one AI entry point (its label is now translated), and the **account menu** behind the avatar holds language, theme, Settings, Help (the documentation site) and sign-out. The topbar's AI search box, its language toggle and the sidebar's theme select are gone.

- **Refresh History is one filterable table, and a run's diagnostics are its own page** (#535). The menu, breadcrumb and title say **Refresh History** (갱신 이력) instead of Refresh Jobs / Run History. `/refresh-jobs` lists runs from `GET /builds` in one table — Run ID, Table, Status, Started, Duration, Snapshot — with search and a status filter kept in the URL (`?q=&status=`), so coming back from a detail keeps them. The KPI cards and the list-beside-detail layout are gone. `GET /builds` does not say which table a run refreshed or which snapshot it produced, so those cells are `—` with the reason (kpubdata-builder#844 asks for them); duration is finished minus started, `—` when either is missing. A row, or its run id link from the keyboard, opens `/refresh-jobs/:id` — stage progress, failure evidence, spec digest and the event log, with a link back; an older `?run=` link opens the same detail. At 390px the table scrolls inside its own focusable region.
- **A compact page header** (#522). The shared `PageHeader` drops the eyebrow label above the title (the topbar breadcrumb already says where you are) and every page stops passing one. The page title is 20px/600 — the largest text in the app — an optional metadata line is 12px, and the description is one line, cut with its full text on hover, so a page's object and work area start right under the header. Identifiers in the metadata line (table ids, run ids) are monospace. The type sizes are theme tokens (`text-page-title`, `text-meta`). Every app page still has one `<h1>`, and a test fails if anything sits above it in the header.
- **Catalog compares sources in a table instead of a card grid** (#529). One row per source, with columns Source (title and `provider.dataset`), Provider, Access (service key; 활용신청 required, not required or unknown, linking to the application page), Maturity, Tables made and Daily quota — every cell from a Builder contract field. `CatalogDataset` carries no institution name, licence (공공누리) or maturity grade, so Catalog shows none of the first two and reads maturity as unknown. `application` null or absent is "application unknown", never "not required"; a missing `quota` is `—`. Tables made come from `GET /datasets` sources; a source with no match is "none" only when Builder's `total` shows the list is complete, otherwise `—`. A new **Needs an application only** filter joins Search, Provider and Service key. At 390px the page does not scroll sideways — the table scrolls inside its own focusable region.
- **Quality Center lists actionable quality issues across tables in one table** (#536). Instead of one run picked through Dataset/Run/Source/Stage selectors with KPI cards, a legend, a trend and a rule pass-rate card, it reads every table's latest refresh (`GET /builds/{run_id}/quality`, four at a time, first 100 tables — Builder's `total` says when there are more) and shows each WARN/FAIL result and each schema drift finding as a row: Table, Source, Rule, Column, Status, Actual / threshold, Affected / evaluated rows and Snapshot (run). Filters are Status (FAIL, WARN, Schema drift), Table and Category, kept in the URL. One line counts tables that need attention, passed, were not evaluated (N/A — never counted as passed) and could not be read; refreshes with nothing evaluated, partial results or an unreadable quality are each one line of links. Each row links to Table Detail's Quality tab for that run and source, which keeps the per-table deep dive; an older link's `?run=` that is not the table's latest points there instead of silently showing the latest. kpubdata-builder#843 asks for one cross-table call.
- The kpubdata boundary gate also fails on kpubdata's own settings — `KPUBDATA_MODE`, `KPUBDATA_REPLAY_DIR`, `KPUBDATA_CACHE_*`, `KPUBDATA_<PROVIDER>_API_KEY` — now that replay and provider keys are Builder's to set (#541, #542). Builder's `KPUBDATA_BUILDER_*` and Studio's `KPUBDATA_STUDIO_*`/`KPUBDATA_CONFIG_OUT` stay allowed.
- The real-Builder E2E starts Builder with its own replay mode (#541): `serve --replay` replays the fixtures Builder ships (kpubdata-builder#837), so `npm run test:e2e:real` runs the public-API scenario with no options, no network and no service key. `--replay-dir` / `STUDIO_REPLAY_DIR` now pass a directory to `serve --replay-dir`. The runner no longer sets `KPUBDATA_MODE`, `KPUBDATA_REPLAY_DIR` or a placeholder data.go.kr key; it asks `serve --help` whether the Builder checkout supports replay and skips the scenario when it does not.
- **Statuses show four different meanings, not one pill each** (#524). Across the status axes, run statuses, quality results and stage statuses: a known value that needs no action (Healthy, Complete, Succeeded, Available, PASS, completed) is plain text; a known value that needs action (Stale, Degraded, Partial, Failed, application required, WARN, FAIL, …) is a bordered badge with its word — and, on the status axes, its axis; Builder's explicit `unknown` is the muted word "Unknown" ("알 수 없음"), read aloud by screen readers; a value Builder did not send is `—` with a tooltip saying KPubData Builder did not provide it; nothing evaluated stays N/A. An unknown is never turned into `—`, and a missing value is no longer shown as `unavailable` or "Unknown status".

### Fixed

- **A source's `param_grid` and `gold` survive editing** (#601). - **The Korean screen no longer shows English labels left in `ko.json`** (#588). #562 moved hard-coded English into the locale files but copied most new Korean values as the English text, so Run detail, Table Detail, Publish, Reports, the menu groups and the shared `labels.*` read "Pipeline / Stage Progress", "Recent Runs", "Blockers", "Status". - **Declared codes and text columns are no longer offered as a chart measure** (#590, contract 1.61.0). #582 kept `logical_type: identifier` off the Y axis, but a code a kpubdata spec declares and that is stored as a number keeps its numeric logical type and carries only `semantic.kind: code`, and a plain text column was still a Y candidate whose numeric-looking values were converted — `"007"` was drawn as 7. **Show as chart** now offers as Y only a column whose values travel as `number` or `decimal_string` and that is neither an identifier nor a declared code; every column stays available as X.
